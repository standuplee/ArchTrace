# ArchTrace PRD — 건축물 생애주기 통합 레이크하우스

Oct 7, 2026 · @과천문원중

## 개요

ArchTrace는 건축물대장 스냅샷과 인허가·말소 데이터를 하나의 레이크하우스에 쌓아, 건물 하나가 허가부터 멸실까지 어떻게 변해왔는지 조회할 수 있게 만드는 개인 프로젝트다. 데이터 엔지니어 채용 요건인 레이크하우스 설계, 변경 이력 관리, 고가용성 파이프라인을 실제 공공데이터로 경험하는 것이 목적이다.

**해결하려는 문제.** 건축물대장은 "현재 상태"만 보여주고, 인허가·대장·말소대장은 서로 직접 연결되는 키가 없는 경우가 많다. 그래서 한 건물의 증축, 용도변경, 멸실 이력을 한 번에 보려면 여러 데이터를 수작업으로 맞춰야 한다.

**왜 이 데이터인가.** 계층 구조(총괄표제부 → 표제부 → 층별 → 전유부), 시간에 따른 변경, 소스 간 엔티티 매칭이라는 데이터 엔지니어링의 핵심 난제를 모두 갖고 있다.

## 목표와 비목표

6주 안에 한 개 구의 건축물 생애주기를 Trino SQL 한 번으로 조회할 수 있는 파이프라인을 완성하는 것이 목표다.

**목표**

1. 건축HUB 원본을 변경 없이 보관하고, 언제든 원본부터 재처리할 수 있는 레이크하우스를 만든다.
2. 스냅샷 간 변경을 감지해 SCD Type 2 이력과 이벤트 로그로 남긴다.
3. 인허가와 대장을 매칭하고, 매칭 근거와 신뢰도를 함께 기록한다.
4. 설계 결정을 ADR로 문서화해 면접에서 그대로 설명할 수 있게 한다.

**비목표**

- 전국 단위 적재. 첫 버전은 한 개 구로 제한하고, 확장은 설계로만 대비한다.
- 클라우드 배포. 로컬 Docker Compose에서만 운영한다.
- 대시보드나 웹 서비스 같은 최종 사용자용 UI. 결과물은 테이블과 SQL이다.
- 실거래가·GIS 등 외부 데이터 결합. 후속 확장으로 둔다.

## 사용자와 핵심 질문

주 사용자는 SQL로 건물 이력을 분석하는 데이터 분석가이고, 아래 다섯 질문에 답할 수 있으면 프로젝트가 성립한다.

| # | 질문 | 답하는 테이블 |
| --- | --- | --- |
| Q1 | 이 건물은 언제 허가받고, 착공하고, 사용승인을 받았나? | gold.building\_lifecycle |
| Q2 | 지난 달 대비 용도변경·증축된 건물은 어떤 것인가? | silver.building\_event |
| Q3 | 2026년 1월 시점에 이 건물의 주용도는 무엇이었나? | silver.building (SCD2) |
| Q4 | 사용승인 후 한 번도 변경 없이 멸실된 건물의 평균 수명은? | gold.building\_lifecycle |
| Q5 | 인허가 중 대장과 매칭되지 않은 건은 몇 건이고 왜인가? | silver.permit\_building\_xref |

부 사용자는 채용 면접관이다. 파이프라인 구조, 장애 대응, 설계 근거를 10분 안에 이해할 수 있어야 한다.

## 범위

첫 버전은 서울 마포구(시군구코드 11440) 한 개 구를 대상으로 하고, 아래 여섯 개 데이터셋을 수집한다.

| 데이터셋 | 출처 | 수집 방식 | 활용 |
| --- | --- | --- | --- |
| 총괄표제부 | 건축HUB | 대용량 파일, 월별 스냅샷 | 단지·복합건물 단위 상위 구조 |
| 표제부 | 건축HUB | 대용량 파일, 월별 스냅샷 | 건물(동) 단위 핵심 상태 |
| 층별개요 | 건축HUB | 대용량 파일, 월별 스냅샷 | 층별 용도·면적 |
| 전유부 | 건축HUB | 대용량 파일, 월별 스냅샷 | 호실 단위 |
| 건축인허가 | 공공데이터포털 API | 법정동 단위 페이지 조회 | 허가·착공·사용승인 일자 |
| 말소대장 | 건축HUB | 대용량 파일 | 멸실 확정 |

기간은 수집 시작 시점부터 매월 스냅샷을 쌓는다. 그 이전 이력은 사용승인일·인허가 일자·말소일로 역산하고, 건축HUB에서 과거 시점 파일을 받을 수 있다면 백필한다. 정확한 파일 단위와 필드는 활용신청 후 명세서로 확정한다.

## 아키텍처와 기술 스택

모든 구성요소는 로컬 Docker Compose 위에서 돌고, raw 버킷의 원본이 유일한 원천 진실이다.

&#91;embedded content: ArchTrace 아키텍처 · 수집에서 조회까지 6단계\]

변환 단계가 커밋한 스냅샷을 Trino가 같은 카탈로그로 읽기 때문에, 쓰는 쪽과 읽는 쪽이 항상 같은 테이블 버전을 본다.

| 구성요소 | 선택 | 이유 |
| --- | --- | --- |
| 스토리지 | MinIO | S3 API 호환, 클라우드 구조를 로컬에서 재현 |
| 테이블 포맷 | Apache Iceberg | 스냅샷, time travel, MERGE, 스키마 진화 |
| 카탈로그 | Iceberg REST + Postgres | PyIceberg와 Trino가 같은 카탈로그 공유, 재시작해도 유지 |
| 처리 | Python + PyIceberg | 한 개 구 규모는 Spark 없이 충분, 확장 시 교체 |
| 쿼리 | Trino 470 | Iceberg MERGE와 메타데이터 테이블 지원 |
| 오케스트레이션 | Dagster | 에셋 단위 계보가 raw → gold 추적성 요구와 맞음 |
| 실행 환경 | Docker Compose | 누구나 같은 환경을 명령 하나로 재현 |

## 데이터 모델

건물의 키는 관리건축물대장PK(mgmBldrgstPk), 땅의 키는 19자리 PNU로 통일한다. PNU는 시군구 5 + 법정동 5 + 대지구분 1 + 본번 4 + 부번 4이며, 대장의 대지구분(0=대지, 1=산)을 PNU 체계(1=일반, 2=산)로 변환해야 한다. 변환 규칙은 명세서로 검증 후 확정한다.

| 레이어 | 테이블 | 키 | 파티션 | 역할 |
| --- | --- | --- | --- | --- |
| raw | MinIO `raw/` | 파일 경로 | snapshot=YYYYMM | 원본 파일 그대로 보관 |
| bronze | bldrgst\_recap\_title, bldrgst\_title, bldrgst\_floor, bldrgst\_unit | mgmBldrgstPk + snapshot\_ym | snapshot\_ym | 스냅샷 원본 적재, append-only |
| bronze | permit\_basis | 인허가PK | 수집일 | 인허가 원본 |
| bronze | demolished\_register | mgmBldrgstPk | 수집일 | 말소대장 원본 |
| silver | building | mgmBldrgstPk + valid\_from | 없음 | SCD2 이력 (valid\_from, valid\_to, is\_current, record\_hash) |
| silver | building\_floor, building\_unit | mgmBldrgstPk + 층/호 | 없음 | 정제된 하위 구조 |
| silver | permit | 인허가PK | 없음 | 허가·착공·사용승인 일자 정제 |
| silver | permit\_building\_xref | 인허가PK + mgmBldrgstPk | 없음 | 매칭 결과, 방식, 점수 |
| silver | building\_event | event\_id | event\_date 연도 | PERMITTED, STARTED, APPROVED, EXTENDED, USE\_CHANGED, DEMOLISHED + 출처 |
| gold | building\_lifecycle | mgmBldrgstPk | 없음 | 건물 1행 요약: 주요 일자, 증축 횟수, 용도 이력, 매칭 신뢰도 |

building\_event의 출처 컨럼은 이벤트가 스냅샷 비교에서 나왔는지 날짜 역산에서 나왔는지를 구분한다.

## 기능 요구사항

핵심은 변경 감지(F3)와 인허가 매칭(F4)이며, 나머지는 이 둘을 받치는 기반이다.

| ID | 기능 | 수용 기준 |
| --- | --- | --- |
| F1 | 원본 보관 | 내려받은 파일을 수정 없이 `raw/` 에 저장하고, 파일명·크기·SHA-256·수집 시각을 기록한다. 같은 해시의 파일은 다시 저장하지 않는다. |
| F2 | bronze 적재 | 스냅샷 단위로 적재하며, 같은 스냅샷을 두 번 적재해도 행 수가 늘지 않는다(파티션 overwrite). |
| F3 | 변경 감지 + SCD2 | 업무 컨럼 해시로 신규·변경·사라짐을 분류하고, silver.building에 MERGE한다. 컨럼 단위 비교로 증축(연면적 증가)과 용도변경을 이벤트로 남긴다. |
| F4 | 인허가 ↔ 대장 매칭 | PNU 일치를 1차 조건으로, 건물명·동명 유사도, 사용승인일, 연면적 차이로 점수를 매긴다. 매칭 방식과 점수를 함께 저장하고 미매칭 건은 사유를 남긴다. |
| F5 | 멸실 확정 | 스냅샷에서 사라진 건물은 말소대장과 대조해 DEMOLISHED로 확정하고, 말소대장에 없으면 검토 대상으로 분류한다. |
| F6 | 과거 이벤트 역산 | 수집 이전 이력을 일자 컨럼으로 생성하고 출처를 ‘날짜 역산’으로 표시한다. |
| F7 | 생애주기 요약 | gold.building\_lifecycle로 핵심 질문 Q1\~Q5에 SQL 한 번으로 답할 수 있다. |
| F8 | 오케스트레이션 | Dagster 에셋으로 raw → gold 계보를 정의하고, 월 1회 스케줄과 수동 백필을 모두 지원한다. |

## 비기능 요구사항

모든 단계는 멱등해야 하며, 같은 입력으로 두 번 돌려도 결과가 같아야 한다.

| 항목 | 요구사항 | 검증 방법 |
| --- | --- | --- |
| 멱등성 | 재실행 시 중복 행·중복 이벤트가 생기지 않는다. | 같은 스냅샷 2회 실행 후 행 수·해시 비교 |
| 재처리 | 파서·매칭 규칙이 바뀌면 raw부터 다시 만들 수 있다. | silver 삭제 후 재생성, gold 결과 동일 여부 |
| 영속성 | 컨테이너를 재시작해도 카탈로그와 데이터가 유지된다. | `docker compose restart` 후 테이블 목록 확인 |
| 데이터 품질 | 하위 테이블의 mgmBldrgstPk는 모두 표제부에 존재한다. PNU는 19자리 숫자다. | 적재 후 자동 검사, 실패 시 다음 단계 중단 |
| 장애 대응 | API 호출 실패는 재시도하고, 실패 건만 다시 수집할 수 있다. | 수집 중 컨테이너 강제 종료 후 재개 |
| 확장성 | 대상 지역을 설정값으로만 늘릴 수 있다. | 두 번째 구 추가 시 코드 변경 없이 동작 |
| 추적성 | gold의 모든 행은 원본 파일과 스냅샷까지 거슬러 올라갈 수 있다. | 임의 건물 1건의 계보 수동 추적 |

## 성공 지표

6주 차 종료 시점에 아래 항목을 모두 충족하면 성공으로 본다. 수치 목표는 실제 데이터를 본 뒤 2주차에 확정한다.

- [ ] 핵심 질문 Q1\~Q5에 각각 SQL 한 번으로 답할 수 있다.
- [ ] 하위 테이블 키 무결성 검사 통과율 100%.
- [ ] 같은 스냅샷 재실행 시 결과 차이 0행.
- [ ] 인허가 중 대장과 매칭된 비율과, 미매칭 사유별 건수를 보고할 수 있다.
- [ ] 두 개 이상의 스냅샷으로 변경 이벤트가 1건 이상 감지된다.
- [ ] ADR 3건 이상과 아키텍처 다이어그램이 README에 있다.

## 리스크와 대응

가장 큰 리스크는 과거 스냅샷을 못 구해 변경 감지를 6주 안에 검증하지 못하는 것이다.

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 과거 스냅샷 파일을 받을 수 없음 | 높음 | 여러 달치를 받을 수 없으면 한 스냅샷을 일부 값만 바꾼 합성 스냅샷으로 로직을 먼저 검증하고, 실제 변경은 다음 달부터 쌓는다. |
| 인허가와 대장 사이에 공통 키가 없음 | 중간 | 점수 기반 매칭을 설계하고 매칭률 자체를 결과물로 낸다. |
| API 승인 지연·호출 한도 | 중간 | 대용량 파일을 주 수집 경로로 쓰고, API는 인허가와 검증용으로만 쓴다. |
| 코드 체계·필드명이 예상과 다름 | 중간 | 1주차에 명세서를 보고 매핑 표를 먼저 만든다. |
| MinIO 이미지 배포 정책 변경 | 낮음 | 태그를 고정하고, 필요하면 다른 S3 호환 스토리지로 교체한다. |
| 취업 준비와 일정 충돌 | 중간 | 주차별 산출물을 작게 유지해, 어느 주차에서 멈춰도 설명 가능한 상태로 둔다. |
